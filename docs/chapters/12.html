Пам’ять і багатокористувацький діалог

Результат навчання

Зберігати історію ізоляційно, будувати контекст за бюджетом і не плутати повідомлення користувача з системною політикою.

Пам’ять діалогу — це дані, які ваш застосунок передає у наступний запит. Модель сама не має доступу до SQLite і не пам’ятає попередній HTTP-виклик. Короткочасна пам’ять містить останні повідомлення, довгострокова може зберігати профіль або знайдені факти. Чітко визначте, що можна зберігати, на який строк і як видаляти. Не накопичуйте приватні дані лише тому, що вони можуть колись знадобитися. Видалення розмови має прибирати також summaries, embeddings і кеші, які з неї походять.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Ізоляція визначається серверною особою користувача та session ID. Кожен запит до messages повинен перевіряти user_id; session ID без owner недостатній. Використовуйте параметризований SQL. Не приймайте user_id як довірений параметр клієнта. Зберігайте роль і порядок повідомлень; user не повинен створювати role=system. У контексті система визначає policy, а історія — предмет розмови. Старий tool output не стає авторитетною інструкцією лише тому, що потрапив у memory.

Повна історія швидко переповнює window. Sliding window проста, але може втратити ранню вимогу. Summary економить токени, але є генеративним перетворенням і може спотворити факт. Зберігайте оригінал, версію summary та посилання на повідомлення. Hybrid memory поєднує останні turns, summary і retrieval релевантних фактів; це покращує покриття ціною складності. Підбирайте стратегію на діалогових тестах, де важливий факт з’являється на початку й потрібен наприкінці.

Термінологія

Turn
Пара користувацької репліки та відповіді. Обрізання між ними може створити дивний контекст.
Session isolation
Дані однієї розмови й власника не мають потрапляти іншому. ID має сенс лише разом з авторизацією.
Summary drift
Поступове спотворення фактів під час повторного підсумовування. Перевіряйте summary на ground truth.
Retention
Правило строку зберігання й видалення. Воно поширюється на похідні дані, а не лише таблицю messages.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

History tokens ≤ window − system − retrieval − question − output reserve.

Для window=8000, system=500, retrieval=3000, question=200 і reserve=1000 історії лишається 3300. Якщо кожен turn коштує близько 600 токенів, поміститься приблизно 5 turns, а не весь місяць розмов. Це лише оцінка: токени рахуються tokenizer моделі. Лабораторний baseline використовує умовну ціну слів, щоб протестувати порядок і budget, але у реальній інтеграції замініть її точним counting.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Memory repository + context policy

Repository забезпечує ізоляційне зберігання; context policy вирішує, які записи передати моделі. Це різні відповідальності: скорочення контексту не повинно видаляти оригінальну історію.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Ставте owner у кожен query

Це захищає навіть якщо session ID вгадали або скопіювали. Перевірка лише на UI недостатня.

Зберігайте оригінал

Summary — похідний артефакт. Його можна перегенерувати, якщо модель або рубрика змінилися.

Рахуйте токени перед викликом

Краще керовано скоротити історію, ніж отримати context overflow.

Окремо зберігайте policy

Не дозволяйте історії додавати system role. Це трохи обмежує гнучкість, але захищає межу довіри.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

Спільний global list

Користувачі бачать чужі повідомлення, особливо під concurrency. Потрібен owner-scoped repository.

Вічне summary of summary

Помилки накопичуються. Періодично підсумовуйте з оригіналів і перевіряйте факти.

LIMIT без ORDER BY

Порядок рядків не гарантований. Явно сортуйте за sequence або timestamp+ID.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Створіть messages з owner, session, seq, role та text.
  2. Append приймає лише user/assistant і параметризований SQL.
  3. Read відбирає за owner+session та явним seq.
  4. Context builder бере останні повні повідомлення у межах бюджету, не змінюючи збережені дані.
Завантажити повний виконуваний приклад 12.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 12.py. Word-based budget is a toy; use model tokens in lab."""
import sqlite3
import unittest

class Memory:
    def __init__(self):
        self.db = sqlite3.connect(':memory:')
        self.db.execute('CREATE TABLE messages(id INTEGER PRIMARY KEY,owner TEXT,session TEXT,role TEXT,text TEXT)')
    def append(self, owner, session, role, text):
        if role not in {'user', 'assistant'}:
            raise ValueError('Role not permitted')
        self.db.execute('INSERT INTO messages(owner,session,role,text) VALUES(?,?,?,?)', (owner, session, role, text))
    def read(self, owner, session):
        return self.db.execute('SELECT role,text FROM messages WHERE owner=? AND session=? ORDER BY id', (owner, session)).fetchall()

def window(messages, budget):
    if budget < 0:
        raise ValueError('Invalid budget')
    selected, used = [], 0
    for message in reversed(messages):
        cost = len(message[1].split())
        if used + cost > budget:
            break
        selected.append(message)
        used += cost
    return list(reversed(selected))

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 12.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_owner_and_order(self):
        memory = Memory()
        memory.append('A', 'same', 'user', 'first')
        memory.append('B', 'same', 'user', 'private')
        memory.append('A', 'same', 'assistant', 'second')
        self.assertEqual(memory.read('A', 'same'), [('user', 'first'), ('assistant', 'second')])
        with self.assertRaises(ValueError):
            memory.append('A', 'same', 'system', 'override')
        memory.db.close()
    def test_budget(self):
        data = [('user', 'one two'), ('assistant', 'three four')]
        self.assertEqual(window(data, 2), [data[1]])
        self.assertEqual(window(data, 1), [])

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Проведіть два паралельні діалоги різних користувачів з однаковим session ID. Додайте факт на початку, 10 сторонніх turns і питання про ранній факт. Порівняйте sliding window та summary. Виміряйте токени, factuality та кількість пропущених умов. Реалізуйте видалення session і перевірте похідні summaries. Артефакти: schema, isolation tests, діалоговий eval і retention policy.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Однакові session IDs різних owner не змішують історії.
  • Повідомлення повертаються у стабільному порядку.
  • Budgeted context не перевищує бюджет; oversize message має явну політику.

Ручна оцінка

  • Чи збереглося раннє важливе обмеження?
  • Чи summary не додав нових фактів?
  • Чи користувач може видалити пам’ять?

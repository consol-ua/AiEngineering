Tools та контрольовані агенти

Результат навчання

Реалізувати bounded tool loop, перевіряти дозволи та аргументи до виконання й не виконувати довільний код моделі.

Агент — система, де модель може пропонувати наступну дію, отримати результат і продовжити. Не кожен workflow потребує агента. Якщо послідовність «пошук → відповідь» відома, звичайний pipeline простіший і легше тестується. Агент корисний, коли потрібно обрати з кількох дозволених операцій залежно від проміжного результату. Ціна — додаткові виклики, складніший debug і ризик циклів. Почніть із двох read-only tools і мінімальної кількості кроків.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Tool call від моделі — пропозиція, а не дозвіл. Сервер перевіряє назву, schema аргументів, права користувача, бюджет і безпечність операції. Registry має містити тільки дозволені callable. Не робіть getattr за довільним рядком, eval чи shell execution. Tool output також недовірений: вебсторінка може містити prompt injection. Передавайте моделі лише необхідні дані та не дозволяйте output змінити policy. Для дій із побічними ефектами додавайте явне підтвердження конкретних аргументів.

Loop має умови завершення: фінальна відповідь, step limit, token budget, deadline або помилка. Повтор одного tool call може бути ознакою зациклення; fingerprint виклику допомагає помітити це. Зберігайте trajectory: назва tool, валідовані args, status і час, але не секрети. Agent success оцінюйте за досягненням задачі, а не за кількістю успішних API-викликів. Можна мати ідеальний tool log і неправильну фінальну відповідь.

Термінологія

Tool schema
Формат аргументів та результату. Він допомагає моделі запропонувати виклик, але перевірка залишається у сервері.
Allowlist
Явний набір дозволених tools. Усе інше відхиляється за замовчуванням.
Trajectory
Послідовність рішень, викликів і результатів. Це основа debug та evaluation агентів.
Human-in-the-loop
Людина підтверджує конкретну дію. Загальна згода «використовуй tools» не має автоматично дозволяти платіж чи видалення.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

Max tool calls ≤ step_limit; worst-case cost ≈ ΣLLM calls + Σtool costs.

Якщо loop дозволяє 5 кроків, кожен може містити LLM-виклик і пошук, бюджет не дорівнює вартості одного запиту. За 2 секунд LLM і 0,3 секунди tool можливий час понад 11,5 секунди без retries. Для паралельних незалежних tools latency зменшується, але concurrency і навантаження зростають. Ліміт кроків захищає ресурси, однак іноді зупиняє корисну задачу; повертайте пояснення, а не мовчазно урізану відповідь.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Command dispatcher with policy gate

Registry з’єднує назву з функцією; gate перевіряє аргументи і права перед виконанням. Планування не може обійти gate. Окремий read-only режим спрощує перший реліз і зменшує ризик побічних ефектів.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Почніть із read-only

Пошук і простий калькулятор достатні для навчання. Write tools потребують audit та підтвердження.

Обмежуйте кроки

Step budget простий і перевірюваний. Додайте deadline, бо один завислий tool все одно може блокувати loop.

Валідуйте аргументи

Число має бути скінченним; query має мати ліміт. JSON від моделі не є довіреним.

Зберігайте trace

Без trajectory складно зрозуміти, де агент помилився. Редагуйте чутливі аргументи.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

eval як калькулятор

Виконає довільний код. Використайте дозволені операції або обмежений AST parser.

Довільні tools із назви

getattr може відкрити небезпечну функцію. Тільки allowlisted registry.

Нескінченний self-correction

Модель може повторювати неправильну дію. Зупиняйте loop і повідомляйте про ліміт.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Створіть registry add/search із фіксованими схемами.
  2. Перевірте tool name, набір ключів, типи та скінченність значень.
  3. Реалізуйте dispatch і bounded sequence без LLM.
  4. У лабораторній додайте model planner; збережіть той самий dispatcher як єдину точку виконання.
Завантажити повний виконуваний приклад 11.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 11.py. Allowlisted tools, no eval, no external effects."""
import math
import unittest

def finite_number(value):
    return type(value) in (int, float) and math.isfinite(value)

def add(args):
    if not isinstance(args, dict) or set(args) != {'a', 'b'} or not all(finite_number(v) for v in args.values()):
        raise ValueError('Require finite a and b')
    result = args['a'] + args['b']
    if not finite_number(result):
        raise ValueError('Result overflow')
    return result

TOOLS = {'add': add}

def dispatch(name, args):
    if name not in TOOLS:
        raise ValueError('Tool not allowed')
    return TOOLS[name](args)

def execute(calls, limit=5):
    if limit < 1 or len(calls) > limit:
        raise ValueError('Step limit exceeded')
    return [dispatch(call['name'], call['args']) for call in calls]

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 11.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_allowed(self):
        self.assertEqual(execute([{'name': 'add', 'args': {'a': 2, 'b': 3}}]), [5])
    def test_policy(self):
        with self.assertRaises(ValueError):
            dispatch('shell', {})
        for args in [{'a': True, 'b': 1}, {'a': math.nan, 'b': 1}, {'a': 1, 'b': 2, 'extra': 0}]:
            with self.assertRaises(ValueError):
                dispatch('add', args)
        with self.assertRaises(ValueError):
            execute([{}]*6)

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Побудуйте агента з пошуком документів та калькулятором лише з add і multiply. Дайте 10 задач, частина з яких не потребує tools, а частина провокує unknown tool чи повтор. Максимум 5 кроків і загальний deadline. Підготуйте manual approval flow для уявної write-дії, але не підключайте її до реального зовнішнього сервісу. Артефакти: registry, policy tests, trajectories і оцінка task success.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Unknown tool та зайві аргументи відхиляються до виконання.
  • NaN, infinity і bool замість number не приймаються.
  • Послідовність понад step limit не виконується.

Ручна оцінка

  • Чи tools потрібні для задачі, а не додані заради моди?
  • Чи користувач бачить, що саме підтверджує?
  • Чи tool output не змінює policy?

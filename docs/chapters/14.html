Безпека й observability

Результат навчання

Визначити межі довіри, перевірити доступ до evidence й додати метрики без витоку приватних даних.

AI-система додає нові поверхні атаки, але не скасовує звичайну безпеку вебзастосунку. Авторизація, parameterized SQL, обмеження body, секрети та ізоляція tenant усе ще критичні. Prompt injection відрізняється від класичної ін’єкції тим, що зловмисний текст намагається змінити поведінку моделі через її мовний інтерфейс. Він може бути в question, документі або tool output. Не можна гарантувати захист одним системним реченням. Потрібні обмежені можливості, детерміновані policy checks і мінімальні привілеї.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Threat model починається з активів і меж довіри: приватні документи, ключ провайдера, історії, tools та compute budget. Намалюйте, звідки приходять дані і хто може їх змінити. Навіть відповідь моделі недовірена, якщо ви відображаєте її як HTML або використовуєте у запиті. Escape текст, перевіряйте URLs і не запускайте SQL чи код. Права перевіряйте до retrieval; видалення forbidden source після generation не прибере факт, який уже потрапив у відповідь.

Observability складається з logs, metrics і traces. Request ID з’єднує HTTP, retrieval і generation; метрики показують частоти та розподіли, а trace — конкретний шлях. Не використовуйте question або user ID як необмежені metric labels: cardinality може перевантажити систему та розкрити дані. Вимірюйте latency, error rate, refusal rate, token usage і retrieval count. Redaction зменшує діагностичність, але це компроміс на користь приватності; за потреби створіть окремий захищений audit, а не публічні логи.

Термінологія

Trust boundary
Межа між контрольованими компонентами та недовіреним входом. Дані після LLM не стають довіреними автоматично.
Least privilege
Компонент має лише необхідні права. Read-only tool не повинен мати credentials для видалення.
Cardinality
Кількість різних значень label у метриках. Висока cardinality збільшує пам’ять і витрати.
Redaction
Вилучення чутливих даних із logs і traces. Regex недостатньо для всіх секретів; краще не логувати їх узагалі.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

Error rate = failed requests / total requests; p95 = latency, нижче якої лежить 95% вибірки.

Для 100 запитів і 7 технічних failures error rate=7%. Контрольована відмова за відсутності evidence не обов’язково технічна помилка: задайте окремий status. Інакше оптимізація error rate змусить систему відповідати там, де вона має відмовитися. Якщо p95 latency=4 секунди, приблизно 5% запитів повільніші; це нічого не каже про тяжкість помилок. Додайте окремий alert на доступ до чужого source, навіть якщо він стався один раз.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Defense in depth

Незалежні перевірки входу, retrieval, tools і rendering зменшують наслідки одного провалу. Вони не повинні покладатися на ту саму генеративну оцінку. Для critical actions є окремий deterministic policy gate.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Перевіряйте ACL до ranking

Forbidden documents не повинні потрапити у context. Це сильніше за UI-фільтрацію.

Логуйте метадані

Request ID, duration і status часто достатні. Повний prompt зручний, але небезпечний.

Обмежуйте ресурси

Body size, concurrency і deadline захищають від resource exhaustion. Надто малі ліміти можуть шкодити легітимним запитам — вимірюйте.

Тестуйте adversarial corpus

Перевірте injection, чужий tenant, HTML і довгі payload. Успіх одного тесту не означає повний захист.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

System prompt як firewall

Модель може порушити інструкцію. Потрібні зовнішні policy checks.

Секрет у context

Навіть корисна модель може повторити його у відповіді. Не передавайте ключі взагалі.

Текст LLM як HTML

Створює XSS-ризик. Відображайте як text або використовуйте перевірений sanitizer.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Завантажити повний виконуваний приклад 14.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 14.py. Deterministic authorization and input policy."""
import unittest

def validate_question(question, maximum=4000):
    if not isinstance(question, str) or not question.strip() or len(question) > maximum:
        raise ValueError('Invalid question')
    return question.strip()

def authorize_chunks(chunks, authenticated_tenant):
    # authenticated_tenant comes from a verified server session, not question JSON.
    if not authenticated_tenant:
        raise ValueError('Authentication required')
    return [chunk for chunk in chunks if chunk['tenant'] == authenticated_tenant]

def audit_event(request_id, status, duration_ms):
    # Intentionally no question, answer, API key or document content.
    return {'request_id': request_id, 'status': status, 'duration_ms': duration_ms}

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 14.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_authorization(self):
        rows = [{'tenant': 'A', 'text': 'ok'}, {'tenant': 'B', 'text': 'private'}]
        self.assertEqual(authorize_chunks(rows, 'A'), [rows[0]])
        with self.assertRaises(ValueError):
            authorize_chunks(rows, '')
    def test_input_and_audit(self):
        for question in ['', '  ', 'a'*4001]:
            with self.assertRaises(ValueError):
                validate_question(question)
        event = audit_event('request-1', 'refused', 12)
        self.assertEqual(set(event), {'request_id', 'status', 'duration_ms'})

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Створіть 10 adversarial сценаріїв: injection у документі, чужий tenant, великий body, unknown tool, HTML у відповіді та спроба витягти ключ. Запустіть їх на pipeline й запишіть expected/actual. Додайте request ID і timings для retrieval/generation. Перегляньте логи вручну на секрети й персональні дані. Артефакти: threat model, test corpus, sanitization policy і dashboard або JSON-звіт метрик.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Forbidden tenant IDs не повертаються з authorize_chunks.
  • Порожні й oversize questions відхиляються до expensive inference.
  • HTML-подібний текст відображається як текст; logs не містять token.

Ручна оцінка

  • Чи policy працює без довіри до моделі?
  • Чи помилка не розкриває credentials або path?
  • Чи метрики не змішують refusal з technical failure?

У нотатках збережіть URL, дату перегляду й одне рішення, яке змінили після читання. Відео — допоміжне пояснення; оцінку лабораторної визначають виконані перевірки й власні артефакти.

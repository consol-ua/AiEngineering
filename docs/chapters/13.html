Локальні моделі та ресурси inference

Результат навчання

Оцінити пам’ять і швидкість локальної моделі, безпечно підняти inference server та порівняти якість із API.

Локальна модель переносить обчислення й операційну відповідальність на вашу машину. Вона може допомогти з приватністю та незалежністю від провайдера, але «без API» не означає «без витрат». Потрібні RAM або VRAM, диск, електроенергія, час завантаження та підтримка. Модель із відкритими вагами не обов’язково має необмежену ліцензію. Перед запуском прочитайте model card і ліцензію, зафіксуйте revision та джерело артефакту. Не запускайте download scripts із невідомого дзеркала лише заради меншого файла.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Квантизація зменшує число бітів на вагу. 4-bit представлення економить пам’ять порівняно з FP16, але додає scales, metadata та можливу втрату якості. Назва Q4 не означає рівно 0,5 byte на весь параметр у реальному файлі. KV cache залежить від context і concurrency, а activations та runtime мають додатковий overhead. Модель може завантажитися й потім отримати OOM на довгому запиті. Плануйте ресурси під одночасні запити, а не лише idle server.

Latency має кілька складових: час до першого токена, prefill і швидкість decode. Tokens per second не описує повний досвід користувача. Batch може підняти throughput, але збільшити очікування окремого запиту. На CPU мала quantized instruct-модель часто зручніша для навчання, ніж велика модель, яка ледве поміщається. Не відкривайте inference port у публічний інтернет без auth і лімітів. Локальний сервер слухає loopback; зовнішній доступ проходить через захищений застосунок.

Термінологія

Quantization
Наближене представлення чисел меншою кількістю бітів. Компроміс між розміром, швидкістю й помилкою залежить від kernels і hardware.
TTFT
Time to first token: очікування першого видимого результату, включно з чергою та prefill.
Throughput
Обсяг обробки за одиницю часу. Високий aggregate throughput не гарантує низький latency одному користувачу.
GGUF
Формат моделей і metadata для екосистеми llama.cpp. Сумісність tokenizer і chat template все одно треба перевірити.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

Weight memory lower bound ≈ parameters × bits / 8; total = weights + KV + activations + runtime.

Для 1 млрд параметрів у 4-bit нижня арифметична оцінка ваг — 0,5 GB, у FP16 — 2 GB. Реальний обсяг більший через metadata та runtime. Якщо доступно 4 GB, не можна автоматично зробити висновок, що FP16-модель із великим контекстом працюватиме. Залиште headroom і виміряйте peak memory на довгому prompt та максимальній concurrency. Навчальний приклад рахує лише нижню межу й навмисно не стверджує готовність hardware.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Local provider behind the same port

Ваш бізнес-код використовує той самий Provider інтерфейс, що й для хмарного API. Змінюється adapter та конфігурація, а не retrieval. Це дозволяє paired comparison моделей на однаковому eval-наборі.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Почніть із малої моделі

Швидкі ітерації важливіші за максимальну кількість параметрів. Потім масштабування можна обґрунтувати eval.

Перевіряйте артефакти

Використовуйте офіційне джерело й checksum якщо наданий. Не вимикайте TLS або trust checks заради запуску.

Тестуйте довгий prompt

Idle RAM недостатня. Peak memory залежить від context і batch.

Вимірюйте end-to-end

Окремо TTFT, decode speed і total latency. Користувачу важлива відповідь, а не лише benchmark kernels.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

Модель помістилася — готово

OOM може статися під навантаженням. Потрібен тест worst-case context.

Публічний port без auth

Будь-хто може витрачати ресурси й отримати доступ до контексту. Використовуйте loopback і захищений proxy.

4-bit завжди краще

Стиснення може знизити якість або бути повільнішим на певному hardware. Порівнюйте власні дані.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Розрахуйте нижню межу пам’яті й перевірте доступні ресурси.

  3. Запустіть llama-server на 127.0.0.1 і перевірте реальний generation request.
  4. Підключіть local adapter і повторіть eval API-моделі на тих самих питаннях.
Завантажити повний виконуваний приклад 13.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 13.py. Lower bound only, not full memory requirement."""
import math
import unittest

def weight_bytes(parameters, bits):
    if type(parameters) is not int or parameters <= 0 or type(bits) is not int or bits <= 0:
        raise ValueError('Positive integer parameters and bits required')
    return math.ceil(parameters * bits / 8)

def sizing(parameters, bits, available_bytes):
    weights = weight_bytes(parameters, bits)
    return {'weight_lower_bound': weights, 'available': available_bytes,
            'weights_fit': weights <= available_bytes,
            'runtime_readiness': 'unverified: KV, activations and runtime not measured'}

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 13.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_lower_bound(self):
        self.assertEqual(weight_bytes(1_000_000_000, 4), 500_000_000)
        self.assertEqual(weight_bytes(1_000_000_000, 16), 2_000_000_000)
        self.assertIn('unverified', sizing(1000, 4, 10000)['runtime_readiness'])
    def test_invalid(self):
        for parameters, bits in [(0, 4), (-1, 4), (10, 0), (True, 4)]:
            with self.assertRaises(ValueError):
                weight_bytes(parameters, bits)

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Виберіть модель, яка вкладається у RAM із запасом. Якщо hardware не дозволяє inference, виконайте sizing і позначте live-перевірку як unrun, а не passed. За доступних ресурсів виміряйте 10 коротких і 5 довгих запитів: TTFT, total latency, tokens/s, RAM та factuality. Порівняйте дві quantization-конфігурації за можливості. Артефакти: model manifest, команда запуску, результати й опис обмежень.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Sizing function відхиляє непозитивні parameters/bits і рахує bytes без прихованого округлення.
  • Live readiness означає representative generation, а не лише відкритий port.
  • Eval позначає unrun inference явно за відсутності hardware.

Ручна оцінка

  • Чи ліцензія дозволяє обраний сценарій?
  • Чи пікова пам’ять виміряна, а не тільки оцінена?
  • Чи якість на українських питаннях достатня?

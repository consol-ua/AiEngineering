Як перевірити, що помічник корисний

Після цього розділу ви зможете

Створити набір перевірок і порівняти дві версії на конкретних результатах.

Evaluation означає оцінювання. Запишіть питання й відомі правильні факти до запуску: «Чи потрібен другий фактор?» → vpn.md і «Так». Для питання поза базою очікуйте відмову. Якщо визначати очікування після відповіді, легко виправдати будь-який результат.

Вам достатньо базового Python: функцій, списків, словників та винятків. Працюємо над одним помічником для інструкцій команди. Спочатку прочитайте приклад, потім запустіть маленький код, після цього виконайте власне завдання. Незрозуміле слово шукайте на сторінці «Нові слова простими словами».

Як це працює на прикладі

Пошук і відповідь перевіряйте окремо. Пошук знайшов правильний документ, але модель перекрутила «потрібно» на «не потрібно». Або модель правильно переказала зовсім не той текст. Метрики джерел покажуть проблему пошуку, читання фактів — проблему відповіді.

Звіт має включати всі питання, навіть технічні збої. Якщо 2 з 10 викликів зламалися, не показуйте лише 8 відповідей. Корисні колонки: очікування, результат, правильно чи ні, час. Якщо оцінює інша модель, порівняйте її рішення зі своїм читанням: вона теж може помилитися.

Нові слова простими словами

Dataset — набір перевірок
Питання, потрібні факти й джерела. JSONL містить один JSON-об’єкт на рядок.
Еталон
Заздалегідь записане очікування. Інші слова допустимі, якщо факт той самий.
MRR
Оцінка місця першого потрібного документа: перше дає 1, друге 1/2, відсутність 0.
Регресія
Нова версія зламала те, що працювало. Старі питання допомагають це помітити.

Не потрібно завчати визначення. Візьміть одне слово й поясніть його на прикладі нашого помічника. Запишіть у нотатках власне речення. Англійську назву залишено, щоб ви впізнали її в документації.

Розрахунок крок за кроком

MRR = сума оцінок першого потрібного результату / кількість питань.

У трьох питаннях джерело перше, друге й відсутнє: 1, 0,5 та 0. MRR = 1,5 / 3 = 0,5. Це оцінка порядку пошуку, не правильності тексту.

Спробуйте змінити одне число

Повторіть розрахунок на аркуші або в Python. Спочатку передбачте результат, потім перевірте. Важливо розуміти, що саме вимірює число: схожість, правильність, пам’ять чи час. Не всі ці показники можна порівнювати між собою.

Корисні звички та їхня ціна

Різні ситуації

Додайте просте, перефразоване, неоднозначне й заборонене питання.

Не підганяйте очікування

Спочатку перевірте факт, а не переписуйте еталон заради зеленого звіту.

Читайте вручну

Збіг id не помітить зміну «потрібно» на «не потрібно».

У кожної зручності є ціна. Додатковий пошук займає час, збереження даних потребує місця, перевірки додають код. Оберіть одну пораду й поясніть, від якої конкретної помилки вона захищає.
РОЗДІЛ 10 · НАВЧАЛЬНА СТОРІНКА 7/12

Типові помилки й виправлення

Лише вдалі випадки

Два красивих приклади не представляють усі запити.

Нуль запусків як успіх

Немає перевірок — немає відомого результату.

Змішати статуси

Не запускали, технічний збій і хибна відповідь — різні ситуації.

Як розібрати помилку

Оберіть один випадок і відтворіть його на своїх навчальних даних. Запишіть три речі: що очікували, що отримали та чому. Виправте причину й повторіть той самий випадок. Додайте перевірку, щоб помилка не повернулася після наступної зміни.

Код: запускаємо та розбираємо

  1. Запишіть питання й джерела до запуску.
  2. Обчисліть Recall@k для питань із джерелом.
  3. Обчисліть MRR для порядку результатів.
  4. Прочитайте факти й запишіть усі збої.
Завантажити 10.py — код і перевірки ↓

Збережіть файл у новій папці. Приклад працює на Python 3.12+ зі стандартною бібліотекою, без платних сервісів. Нижче його основна частина; спочатку розберемо, що роблять функції.

"""Run: python 10.py. Retrieval metrics with explicit empty-run failure."""
import unittest

def recall_at_k(expected, retrieved, k):
    if not expected or k < 1:
        raise ValueError('Ground truth and positive k required')
    return len(set(expected) & set(retrieved[:k])) / len(set(expected))

def mrr(cases):
    if not cases:
        raise ValueError('Zero-test evaluation is not valid')
    total = 0.0
    for expected, retrieved in cases:
        if not expected:
            raise ValueError('Ground truth required')
        for rank, id in enumerate(retrieved, 1):
            if id in expected:
                total += 1 / rank
                break
    return total / len(cases)

Що тут відбувається

  • Пара містить потрібні id й отриманий список.
  • MRR бере першу правильну позицію для кожного питання.
  • Порожній набір питань відхиляється: оцінки без перевірок немає.

Маленький запуск із відомим результатом

Створіть demo.py у тій самій папці, де лежить 10.py. Скопіюйте наступний код і виконайте python demo.py. runpy.run_path() завантажує функції зі збереженого файла; ви не повинні переписувати їх вручну.

import runpy
m = runpy.run_path("10.py")
cases = [(["vpn"], ["vpn"]), (["vpn"], ["other", "vpn"]), (["vpn"], [])]
print(m["mrr"](cases))
print(m["recall_at_k"](["vpn", "policy"], ["vpn", "other"], 2))

Підніміть vpn на перше місце другого списку й порахуйте MRR вручну. Потім спробуйте mrr([]).

Перевірки та обробка помилок

У завантаженому файлі вже є перевірки. Виконайте python 10.py з його папки. Наприкінці має бути OK. Це означає, що перевірки прикладу пройшли, а не що весь майбутній помічник готовий.

class Tests(unittest.TestCase):
    def test_known_metrics(self):
        self.assertEqual(recall_at_k(['a', 'b'], ['b', 'x', 'y'], 3), 0.5)
        self.assertEqual(mrr([(['a'], ['a']), (['a'], ['x', 'a']), (['a'], [])]), 0.5)
    def test_empty(self):
        with self.assertRaises(ValueError):
            mrr([])
        with self.assertRaises(ValueError):
            recall_at_k([], ['a'], 1)

if __name__ == '__main__':
    unittest.main()

assertEqual перевіряє рівність, assertTrue — істинність умови, assertRaises — очікувану помилку. Якщо перевірка не пройшла, прочитайте очікуване й отримане значення. Помилка на неправильному вводі часто є саме потрібною поведінкою.

Підміна зовнішнього сервісу перевіряє ваш код без мережі. Якість справжньої моделі, роботу зовнішньої бази та швидкість на вашому обладнанні перевіряють окремо. У FastAPI перетворюйте очікувані помилки на зрозумілу відповідь користувачу.

Практика: зробіть самостійно

Зробіть перший звіт на 10 питаннях до свого помічника.

Кроки завдання

  1. Створіть 6 питань із бази, 2 поза базою та 2 неоднозначні.
  2. Запишіть очікуваний факт або відмову.
  3. Збережіть відповіді, джерела й час однієї версії.
  4. Перевірте формат, пошук і зміст окремими колонками.
  5. Змініть одну настройку й повторіть ті самі питання.
  6. Покажіть, що покращилось, погіршилось і не змінилось.

Що показати після виконання

  • Файл питань.
  • Два звіти.
  • Розбір трьох помилок.
Почніть із мінімального варіанта. Частини з позначкою «додатково» не потрібні для першого успіху. Якщо зовнішня модель чи обладнання недоступні, виконайте незалежні кроки й запишіть, що саме ще не перевіряли.

Як перевірити свою роботу

Що перевірити кодом

  • Навчальний приклад дає MRR=0,5.
  • Усі питання є у звіті, навіть після винятку.
  • Нуль запусків не дає успіх.

Що перевірити своїми очима

  • Факти прочитані вручну.
  • Відмови поза базою перевірені.
  • Різниця версій пояснена на прикладах.

Як зрозуміти, що завдання виконане

СтанЩо вже зроблено
ПочавПрочитав і запустив готовий приклад.
Базову практику виконавВиконав основні кроки на своїх даних та зберіг результати.
Можу пояснитиПеревірив неправильний випадок, пояснив причину та записав обмеження.

Фінальний проєкт: доказова готовність

Результат навчання

Зібрати асистента з retrieval, джерелами, ізоляцією, оцінюванням і повторюваним запуском та представити чесний release report.

Фінальний проєкт об’єднує компоненти, але його головний результат — доказ, що система виконує обраний контракт. Оберіть вузьку базу знань і конкретного користувача. Асистент для інструкцій одного продукту легше оцінюється, ніж «відповідає на все». Визначте answerable scope, права доступу та поведінку за браку даних. Архітектура має показувати ingest, query, auth, storage, model adapter і evaluation. Не додавайте agents, якщо простий RAG уже вирішує задачу: складність має мати вимірювану причину.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Release report містить версії корпусу, індексу, моделі й промпту, кількість eval-питань, quality metrics, latency і відомі failures. Нуль критичних витоків на тестовому corpus — необхідна умова, але не доказ абсолютної безпеки. Gate перевіряє конкретні вимірювання, а не оптимістичні припущення. Порогові значення обирайте відповідно до ризику й задачі до фінального run. Якщо threshold підібрано після результатів, це демонстрація, а не незалежна перевірка.

Демо має включати успішний запит, відмову, failure залежності та відновлення після restart. Покажіть source link і перевірте його вручну. README має дозволити іншому розробнику відтворити середовище, додати документи, запустити тести й зрозуміти, які перевірки потребують credentials. Secrets вводяться через environment, а не у приклад коду. Backup і deletion policy завершують lifecycle даних. Після release продовжуйте збирати помилки й періодично переглядати eval-набір, не перетворюючи його на єдину ціль оптимізації.

Термінологія

Acceptance gate
Явні умови release: quality, completion, latency і critical safety tests. Gate не повинен приховувати unrun перевірки.
Reproducibility manifest
Версії й конфігурація, потрібні для повторення run. Без них відсотки у презентації не мають стабільного змісту.
Known limitations
Підтверджені межі системи: unsupported мови, stale data, hardware limits, характерні помилки. Це частина продуктового контракту.
Release evidence
Звіти та артефакти конкретної перевірки. Скрипт, який ніколи не запускали, не є доказом.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

Release = quality_pass ∧ safety_pass ∧ reliability_pass ∧ reproducibility_pass.

Умовний навчальний gate може вимагати не менше 30 eval-питань, Recall@3≥0,8, нуль tenant leaks і p95≤5 секунд. Це демонстраційні пороги, не production-рекомендація. Навіть якщо recall=0,9, один critical leak блокує release. Якщо p95 не виміряний, значення unknown не має перетворюватися на pass. Звіт gate повинен повертати список причин, щоб команда розуміла, що саме потрібно виправити або перевірити.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Evidence-driven release

Build створює артефакт; evaluation і smoke перевіряють його конкретну версію; release gate читає звіти. Після зміни моделі або індексу evidence потрібно оновити, а не переносити зелені результати від старого build.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Зменшіть scope

Вузький проєкт із сильними доказами корисніший за багато неперевірених функцій.

Покажіть відмову

Негативне демо демонструє межі. Користувач краще розуміє, коли довіряти системі.

Перевірте чистий запуск

Новий каталог або container має працювати за README. Це виявляє приховані ручні кроки.

Випустіть failure report

Список помилок допомагає планувати наступні зміни; приховування їх створює хибну готовність.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

Demo cherry-picking

Лише три вдалі питання приховують ненадійність. Потрібен повний eval report.

Release без provenance

Невідомо, що саме перевірено. Зберігайте commit і versions.

Optional як required pass

Незапущений live inference не доводить якість. Розділіть passed, failed та unrun.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. З’єднайте компоненти попередніх модулів через стабільні інтерфейси.
  2. Створіть release manifest і policy thresholds.
  3. Реалізуйте gate, який повертає всі причини відмови.
  4. Виконайте clean-start, evaluation, security та backup/restore, потім підготуйте demo.
Завантажити повний виконуваний приклад 16.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 16.py. Illustrative thresholds, not production policy."""
import math
import unittest

POLICY = {'min_questions': 30, 'min_recall': 0.8, 'max_p95_ms': 5000}

def release_gate(report):
    reasons = []
    for key in ['questions', 'recall_at_3', 'p95_ms', 'tenant_leaks', 'clean_start_verified']:
        if key not in report:
            reasons.append('Missing: ' + key)
    if reasons:
        return {'ready': False, 'reasons': reasons}
    for key in ['questions', 'recall_at_3', 'p95_ms', 'tenant_leaks']:
        if type(report[key]) not in (int, float) or not math.isfinite(report[key]) or report[key] < 0:
            reasons.append('Invalid metric: ' + key)
    if reasons:
        return {'ready': False, 'reasons': reasons}
    if report['questions'] < POLICY['min_questions']:
        reasons.append('Insufficient evaluation questions')
    if not POLICY['min_recall'] <= report['recall_at_3'] <= 1:
        reasons.append('Retrieval quality gate failed')
    if report['p95_ms'] > POLICY['max_p95_ms']:
        reasons.append('Latency gate failed')
    if report['tenant_leaks'] != 0:
        reasons.append('Critical tenant leak')
    if report['clean_start_verified'] is not True:
        reasons.append('Clean start unverified')
    return {'ready': not reasons, 'reasons': reasons}

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 16.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_ready(self):
        self.assertTrue(release_gate({'questions': 30, 'recall_at_3': 0.9, 'p95_ms': 1000, 'tenant_leaks': 0, 'clean_start_verified': True})['ready'])
    def test_missing_and_critical(self):
        self.assertFalse(release_gate({})['ready'])
        value = {'questions': 30, 'recall_at_3': 0.99, 'p95_ms': 10, 'tenant_leaks': 1, 'clean_start_verified': True}
        self.assertIn('Critical tenant leak', release_gate(value)['reasons'])
        value['tenant_leaks'] = 0
        value['p95_ms'] = math.nan
        self.assertFalse(release_gate(value)['ready'])

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Побудуйте персонального асистента документації з 10–20 файлами. Обов’язкові функції: auth, owner-scoped retrieval, citations, no-answer, bounded provider calls, persistence і eval на 30 питаннях. Опціонально додайте local model або read-only agent і покажіть його користь окремим експериментом. Підготуйте README, architecture diagram, release report і 5-хвилинне демо із негативним сценарієм. Виконайте peer review за рубрикою нижче та зафіксуйте ще не перевірені можливості.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Gate відхиляє недостатній sample count, missing metrics і tenant leaks.
  • Clean-start smoke, schema tests та owner isolation виконані на поточній версії.
  • Report містить passed/failed/unrun та посилання на артефакти.

Ручна оцінка

  • Користувач може перевірити джерело кожного важливого факту.
  • Інший розробник відтворює запуск і restore за README.
  • Демо показує відмову та відомі обмеження без приховування помилок.

Як працювати з джерелами

Спочатку прочитайте офіційне визначення й мінімальний приклад. Потім поверніться до вашого коду та перевірте припущення: типи входу, ліміти, exceptions і version compatibility. У нотатках збережіть URL, дату перегляду й одне рішення, яке змінили після читання. Відео — допоміжне пояснення; оцінку лабораторної визначають виконані перевірки й власні артефакти.

Надійна інтеграція LLM API

Результат навчання

Створити provider adapter із тайм-аутом, обмеженими повторами й контрольованими помилками; підключити його до FastAPI.

Виклик LLM — зовнішня залежність, яка може бути повільною, недоступною або змінити формат відповіді. Ваш HTTP-сервіс не повинен нескінченно чекати чи повертати користувачеві traceback SDK. Потрібно розділити помилки входу, тимчасову недоступність і некоректний результат. Вхідна помилка не виправиться повтором. Тимчасова 429 чи 503 може зникнути, але повтори мають вкладатися у загальний deadline запиту. Виняток адаптера перетворюється на стабільну помилку продукту, а не копію повідомлення провайдера.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Тайм-аут одного виклику та загальний deadline — різні речі. Три спроби по 15 секунд плюс паузи можуть затримати користувача на хвилину. Визначте бюджет усього запиту, а потім розподіліть його між retrieval, generation і retries. Async cancellation допомагає припинити очікування, але не гарантує, що віддалений сервіс перестав працювати або не нарахував оплату. Тому логічно успішний повтор може коштувати двох генерацій. Для інструментів із побічними ефектами потрібні idempotency keys або заборона автоматичного повтору.

Обмежуйте одночасні запити до провайдера через semaphore або чергу. Якщо всі клієнти відразу повторюють після 429, виникає retry storm. Exponential backoff із jitter розводить спроби у часі. Retry-After враховуйте в межах deadline; не приймайте довільно довгу затримку. Ключі беріть із серверної конфігурації. Не додавайте їх у репозиторій, query string логів чи промпт. У звітах про latency розрізняйте час очікування черги та час самої генерації.

Термінологія

Timeout
Максимальний час очікування окремої операції. Connect, read і total timeout можуть бути різними налаштуваннями SDK.
Deadline
Момент, після якого весь запит більше не має сенсу для клієнта. Повтори й backoff повинні вкластися в цей бюджет.
Idempotency
Повтор операції не створює нового побічного ефекту. Генерація тексту може бути функціонально безпечною, але все одно додати оплату.
Circuit breaker
Після серії збоїв тимчасово відмовляє без виклику залежності. Це зменшує навантаження, але потребує обережного відновлення.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

T_total = ΣT_attempt + ΣT_backoff + T_queue; backoffₙ = min(cap, base × 2ⁿ) + jitter.

Три спроби по 2 секунди з паузами 0,2 та 0,4 дають до 6,6 секунди без черги. Якщо HTTP deadline — 5 секунд, така конфігурація суперечлива. Можна скоротити attempt timeout, кількість спроб або взагалі відмовитися від retry. Оцінюйте також частоту: за p=0,1 тимчасових збоїв два незалежні провали мають ймовірність 0,01, але реальні збої часто корельовані. Під час outage повтор не має очікуваної незалежної переваги.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Bulkhead + adapter

Окремий ліміт конкурентності не дозволяє одному провайдеру зайняти всі ресурси сервера. Адаптер приховує SDK й мапить помилки у власні exception types. Fake реалізує той самий інтерфейс і дозволяє моделювати timeout або transient failure без мережі.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Повторюйте вибірково

Тільки тимчасові помилки та безпечні операції. Повтор 401 або malformed request даремно витрачає час.

Встановіть верхню межу

Обмежте attempts і deadline. Надійність одного клієнта не має погіршувати надійність усіх інших.

Редагуйте логи

Зберігайте request ID, status і тривалість; текст користувача та ключі логувати необов’язково. Менше даних ускладнює діагностику, але захищає приватність.

Проведіть failure injection

Тест із fake timeout сильніший за один успішний live-запит. Однак live-інтеграцію треба окремо перевірити перед production.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

Нескінченні retries

Під час outage накопичують чергу і роблять збій довшим. Визначте чітку відмову.

Sync SDK усередині async route

Блокує event loop і затримує інші запити. Використовуйте async client або контрольований thread pool.

Логи повної відповіді

Можуть містити персональні дані або секрети із контексту. Логуйте мінімальні метадані й використовуйте redaction.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Створіть TransientError і Provider Protocol з async generate().
  2. Огорніть кожну спробу asyncio.wait_for; перетворіть timeout на контрольовану помилку.
  3. Додайте обмежений backoff лише для TransientError.
  4. Протестуйте успіх із другої спроби, permanent error та повільний fake; у API відобразіть їх на стабільні статуси.
Завантажити повний виконуваний приклад 05.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 05.py. Bounded attempt retries with a fake async provider.
A real HTTP adapter must also enforce the overall request deadline.
"""
import asyncio
import unittest

class TransientError(Exception):
    pass

async def generate(provider, question, attempts=2, timeout=0.1, backoff=0.01):
    if attempts < 1 or timeout <= 0 or backoff < 0:
        raise ValueError('Invalid retry policy')
    for attempt in range(attempts):
        try:
            return await asyncio.wait_for(provider(question), timeout)
        except (TransientError, asyncio.TimeoutError) as error:
            if attempt + 1 == attempts:
                raise TransientError('Provider unavailable') from error
            await asyncio.sleep(backoff * 2**attempt)

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 05.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.IsolatedAsyncioTestCase):
    async def test_retry_then_success(self):
        calls = 0
        async def fake(question):
            nonlocal calls
            calls += 1
            if calls == 1:
                raise TransientError('503')
            return 'ok'
        self.assertEqual(await generate(fake, 'q'), 'ok')
        self.assertEqual(calls, 2)
    async def test_permanent_not_retried(self):
        calls = 0
        async def fake(question):
            nonlocal calls
            calls += 1
            raise ValueError('Invalid request')
        with self.assertRaises(ValueError):
            await generate(fake, 'q')
        self.assertEqual(calls, 1)
    async def test_timeout(self):
        async def slow(question):
            await asyncio.sleep(1)
        with self.assertRaises(TransientError):
            await generate(slow, 'q', attempts=1, timeout=0.01)

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Зробіть FastAPI /ask з fake та опціональним реальним адаптером. Додайте semaphore на 5 викликів, timeout і максимум 2 спроби. Прогоніть 20 конкурентних запитів: частина fake-викликів має затримуватися чи повертати transient failure. Збережіть таблицю успіхів, відмов, кількості attempts і latency. Вкажіть, чи ці результати вимірюють лише fake. Для реального провайдера окремо перевірте auth, квоти й JSON-контракт, не друкуючи секрети.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Transient failure повторюється не більше заданого attempts.
  • Permanent failure не повторюється; timeout завершується контрольованим exception.
  • Кількість одночасних generation не перевищує semaphore limit.

Ручна оцінка

  • Чи сума timeout і backoff відповідає HTTP deadline?
  • Чи не містять логи ключів і текстів, які не потрібні?
  • Чи розрізняються outage та неправильні credentials?

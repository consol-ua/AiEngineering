Деплой, навантаження та продуктивність

Результат навчання

Підготувати повторюваний deployment, перевірити persistence і виміряти p50/p95 разом із частотою помилок.

Deployment — відтворення перевіреного середовища, а не просто відкриття порту. Зафіксуйте залежності, runtime, command, variables та storage paths. Контейнер має бути immutable; користувацькі дані зберігаються у persistent volume або зовнішній БД. Якщо SQLite лежить у файловій системі контейнера, rebuild може стерти її. Snapshot не замінює резервну копію та перевірку restore. На безкоштовних хостингах враховуйте sleep: серверні нагадування не працюватимуть під час простою.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Liveness відповідає, чи процес живий; readiness — чи може обслуговувати запит. Healthcheck не повинен щоразу викликати платний LLM: це створить витрати й зайву залежність. Репрезентативний smoke test запускається окремо та перевіряє справжню поведінку. Multiple workers збільшують throughput, але in-memory state між ними не спільний, а фоновий scheduler може стартувати кілька разів. Для SQLite враховуйте один writer і locks; для більшого навантаження зовнішня БД може бути кращою.

Load test повинен перевіряти реалістичний mix запитів, а не лише /health. Warm-up, cold start, довгі inputs і failures впливають на distribution. Closed-loop тест, де клієнт чекає попередню відповідь, може приховати чергу під навантаженням. Вимірюйте arrivals, completion rate, concurrency, latency й resources. Оптимізація caching зменшує latency, але ключ має включати model/prompt/index version і tenant; інакше кеш поверне застарілу чи чужу відповідь.

Термінологія

p50 / p95
Медіана й хвостовий percentile latency. Визначте спосіб обчислення та кількість samples.
Persistent volume
Диск, який не зникає разом із контейнером. Його наявність треба перевірити restart/restore тестом.
Readiness
Здатність обслуговувати роботу зараз. Порт, який слухає, не доводить готовність залежностей.
Cache invalidation
Скидання результату після зміни моделі, промпту, прав чи індексу. Неповний key небезпечніший за повільний запит.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

Little’s law: L = λW у стабільній системі; nearest-rank p = sorted[ceil(p×N)−1].

За 2 запити/с і середньої тривалості 3 секунди в стабільній системі очікується близько 6 запитів у роботі або черзі. Це не рекомендація встановити semaphore=6 без інших перевірок: traffic burst і tail latency можуть вимагати іншого budget. Для 20 samples nearest-rank p95 — 19-й елемент відсортованого списку. Вкажіть convention у звіті, бо interpolated percentile може відрізнятися на малих наборах.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Stateless API, explicit state

HTTP-workers не зберігають важливий state у global lists. БД та індекс мають явні volumes, а scheduler — один owner або окремий процес. Це полегшує restart і горизонтальне масштабування.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Перевіряйте restore

Створіть запис, зробіть backup, відновіть у новому path і прочитайте. Файл backup без тесту ще не гарантує відновлення.

Фіксуйте versions

Зміна dependency під час build може зламати поведінку. Lock або повні pins підвищують повторюваність.

Додавайте timeout і limits

Навантаження без bounds накопичує чергу. Reject може бути кращим за нескінченне очікування.

Рахуйте failures

Latency лише успішних запитів може виглядати чудово при масових timeout. Звітуйте completion rate поруч.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.

Антипатерни

Дані в image layer

Rebuild прибирає результати. Використайте volume і backup.

Кілька scheduler workers

Нагадування дублюються. Визначте single owner або shared locking.

Load test тільки /health

Не перевіряє retrieval та generation. Потрібні representative requests.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Створіть Dockerfile з non-root користувачем і pinned dependencies.
  2. Налаштуйте data volume й одну команду старту.
  3. Реалізуйте health та representative smoke test окремо.
  4. Зберіть latency samples і порахуйте percentiles разом із error rate.
Завантажити повний виконуваний приклад 15.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 15.py. Nearest-rank percentiles, failures remain visible."""
import math
import unittest

def percentile(values, p):
    if not values or not 0 < p <= 1 or any(not math.isfinite(x) or x < 0 for x in values):
        raise ValueError('Valid samples and percentile required')
    ordered = sorted(values)
    return ordered[math.ceil(p*len(ordered))-1]

def report(success_latencies, failures):
    if type(failures) is not int or failures < 0:
        raise ValueError('Invalid failures')
    total = len(success_latencies) + failures
    if not total:
        raise ValueError('No requests executed')
    return {'total': total, 'failures': failures,
            'completion_rate': len(success_latencies)/total,
            'p95_success_only': percentile(success_latencies, 0.95) if success_latencies else None}

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 15.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_percentile(self):
        self.assertEqual(percentile(list(range(1, 21)), 0.95), 19)
        self.assertEqual(percentile([3], 0.5), 3)
    def test_failure_accounting(self):
        self.assertEqual(report([1, 2], 2)['completion_rate'], 0.5)
        self.assertIsNone(report([], 3)['p95_success_only'])
        with self.assertRaises(ValueError):
            report([], 0)
        with self.assertRaises(ValueError):
            percentile([], 0.95)

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Контейнеризуйте фінальний API. Додайте persistent storage, створіть користувача/запис, перезапустіть контейнер і перевірте дані. Виконайте 100 representative requests із concurrency=10 на fake, потім окремий контрольований live-run якщо є квота. Виміряйте cold start, p50/p95, failures і RAM. Зробіть backup та restore у новий каталог. Артефакти: Dockerfile, команда запуску, load script, report та recovery guide.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Percentile function відхиляє порожній набір і невалідні значення.
  • Restart зберігає state; restore читає очікувані записи.
  • Smoke перевіряє /ask, а report містить failures і sample count.

Ручна оцінка

  • Чи hosting sleep сумісний із нагадуваннями?
  • Чи cache key містить tenant і versions?

Векторна база: індекси й життєвий цикл

Результат навчання

Зберігати вектори та метадані, коректно оновлювати й видаляти документи та застосовувати фільтри доступу до ранжування.

Векторна база вирішує не тільки пошук найближчих сусідів. Вона зберігає IDs, вектори, metadata та підтримує оновлення індексу. Exact scan простий, але його час зростає з N×D. Approximate nearest neighbors скорочує пошук ціною можливих пропусків. HNSW будує граф сусідства з кількома рівнями: пошук стартує на грубому рівні й уточнюється нижче. Це не означає, що approximate результат неправильний завжди, але його recall потрібно порівняти з exact baseline.

Цей розділ продовжує наскрізний проєкт асистента документації. Перед початком відкрийте свою попередню реалізацію й перевірте її тести. Запишіть у нотатках, яку поведінку ви очікуєте змінити, які дані потрібні та як будете перевіряти результат. Не відмічайте практичний крок лише за фактом прочитання прикладу: він вимагає власного виконання й артефактів лабораторної.

Механізми та межі

Document ID і chunk ID — різні сутності. Один файл може мати багато chunks; оновлення файла має видалити старі chunks, які більше не існують. Використайте стабільний документний ключ і версію вмісту. Після embedding-моделі іншої розмірності створюйте нову колекцію або повністю переіндексуйте. Не змішуйте старі й нові вектори в одному просторі. Корисний manifest містить model revision, dimensions, normalization, schema version та дату індексації.

Metadata-фільтр — частина безпеки, якщо від нього залежить видимість документа. Спочатку обмежуйте множину кандидатів дозволеним tenant або ACL, потім ранжуйте. Post-filter може видати замало результатів, а в неправильній реалізації — приховати витік лише на UI. Не довіряйте tenant_id, який користувач передав у question: його визначає серверна сесія. Локальний SQLite-приклад у цьому розділі демонструє lifecycle і exact scan, а не є повноцінною ANN-базою; Chroma додається в лабораторній.

Термінологія

ANN
Approximate nearest neighbors: швидший пошук із компромісом recall. Параметри індексу потрібно вимірювати, а не вважати універсальними.
Upsert
Створення або заміна запису за ID. Без стабільних IDs повторна індексація додає дублікати замість оновлення.
Collection
Ізольована група векторів із сумісною конфігурацією. Не змішуйте моделі, навіть якщо dimensions випадково збігаються.
Tombstone
Позначення видаленого запису, який ще може фізично існувати в індексі. Перевіряйте, чи пошук уже не повертає його.

Складіть власний мінісловник: для кожного терміна наведіть приклад із вашого проєкту та один близький термін, із яким його легко переплутати. Пояснення має бути зрозумілим розробнику, який знає Python, але ще не працював із цим компонентом. Якщо можете повторити визначення, але не навести контрприклад, поверніться до механізму на попередній сторінці.

Формули й розрахунки

M_vectors ≈ N × D × bytes_per_coordinate; повний індекс потребує додаткової пам’яті.

100 000 векторів по 384 float32 займають близько 153,6 MB у десяткових одиницях лише для координат. Graph edges, IDs, metadata, кеш і overhead збільшують обсяг. Якщо віддати всі вектори на Python exact scan, час також включає JSON-декодування й виділення пам’яті. Оцінюйте disk, resident RAM і query latency окремо. Збільшення точності ANN може підвищити recall, але також latency; графік Pareto корисніший за одну «найкращу» конфігурацію.

Розрахуйте приклад вручну до запуску коду. Потім змініть одне припущення та запишіть, який результат очікуєте. Перевірка крайніх випадків важливіша за красиву формулу: визначте область допустимих значень, поведінку на порожньому вході та спосіб обробки невідомого результату. Формула спрощує систему; не використовуйте її як гарантію поведінки на даних, яких ви не виміряли.

Архітектура та потоки даних

Repository pattern + versioned index

Application працює з методами upsert, delete_document та search. Адаптер може бути локальним або Chroma. Нова версія індексу готується окремо, перевіряється, а тоді стає активною; це дорожче по диску, але спрощує rollback.

Пройдіть схему зліва направо на одному нормальному й одному невдалому запиті. Для кожної стрілки запишіть формат даних, власника, межу довіри та можливий exception. Визначте, який компонент відповідає за retry, а який — за відмову. Не додавайте дубльовані перевірки без пояснення: незалежні security gates корисні, але два неузгоджені парсери можуть створити різну поведінку.

Архітектурне рішення

У нотатках створіть короткий ADR: контекст, обраний варіант, альтернатива, наслідки та спосіб перевірки. Якщо навантаження, corpus або модель зміняться, які припущення перестануть бути справедливими? ADR потрібен, щоб майбутня зміна була свідомим рішенням, а не повторенням чужого патерну.

Best practices і компроміси

Перевіряйте persistence

Перезапустіть процес і повторіть пошук. In-memory колекція не доводить, що дані переживуть deployment.

Видаляйте за document ID

Після оновлення тексту старі chunks не мають залишатися. Інакше відповідь цитуватиме неактуальну інструкцію.

Фільтруйте до top-k

Пошук лише в дозволеній множині захищає доступ і не втрачає k після post-filter.

Підтримуйте rollback

Старий індекс може займати диск, але рятує від невдалої міграції embeddings.

Оберіть одну рекомендацію, яка збільшує latency або складність, і поясніть, який ризик вона зменшує. «Завжди краще» не є достатнім обґрунтуванням.
РОЗДІЛ 07 · НАВЧАЛЬНА СТОРІНКА 7/12

Антипатерни

Дублі після кожного ingest

Випадкові IDs створюють багато копій одного chunk. Використайте deterministic IDs і upsert.

Права лише на frontend

Клієнт можна обійти. Перевірка tenant має бути в server-side retrieval.

Зміна моделі без rebuild

Старі вектори несумісні з новими запитами. Створіть нову collection і повторіть eval.

Розбір інциденту

Оберіть одну типову помилку й відтворіть її у контрольованому тесті з локальними даними. Запишіть симптом, першопричину, наслідок для користувача та regression test. Потім виправте реалізацію й доведіть, що тест відрізняє неправильну версію від правильної. Не вимикайте assertion, щоб отримати зелений результат: це прибирає доказ, а не помилку.

Покрокова реалізація

  1. Створіть таблицю з primary key (tenant,id) та полями vector, text, source.
  2. Реалізуйте upsert із параметризованим SQL.
  3. Search спочатку читає лише заданий tenant, потім рахує exact cosine.
  4. Тестуйте закриття/відкриття БД, заміну ID і видалення; потім повторіть на Chroma.
Завантажити повний виконуваний приклад 07.py ↓

Нижче — повний core навчального компонента. Він використовує стандартну бібліотеку Python 3.12+, щоб ви могли перевірити логіку без API-ключів. Це baseline конкретної стадії, а не готовий production-сервіс. Інтеграція реальної моделі та зовнішніх залежностей описана у лабораторній.

"""Run: python 07.py. SQLite lifecycle baseline; not an ANN database."""
import json
import sqlite3
import tempfile
from pathlib import Path
import unittest

class Store:
    def __init__(self, path):
        self.db = sqlite3.connect(path)
        self.db.execute('CREATE TABLE IF NOT EXISTS chunks(tenant TEXT,id TEXT,text TEXT,vector TEXT,PRIMARY KEY(tenant,id))')
    def upsert(self, tenant, id, text, vector):
        self.db.execute('INSERT INTO chunks VALUES(?,?,?,?) ON CONFLICT(tenant,id) DO UPDATE SET text=excluded.text,vector=excluded.vector', (tenant, id, text, json.dumps(vector)))
        self.db.commit()
    def rows(self, tenant):
        return self.db.execute('SELECT id,text,vector FROM chunks WHERE tenant=? ORDER BY id', (tenant,)).fetchall()
    def delete(self, tenant, id):
        self.db.execute('DELETE FROM chunks WHERE tenant=? AND id=?', (tenant, id))
        self.db.commit()
    def close(self):
        self.db.close()

Тести й обробка помилок

Завантажений файл містить наведені нижче тести. Запустіть його у терміналі командою python 07.py. Ненульовий exit code означає невдачу. Для негативних тестів спершу передбачте помилку, потім виконайте запуск. Успішний fake-тест перевіряє контракт і control flow, але не якість моделі, реальну мережу чи достатність hardware.

class Tests(unittest.TestCase):
    def test_lifecycle_and_isolation(self):
        with tempfile.TemporaryDirectory() as directory:
            path = str(Path(directory) / 'index.db')
            store = Store(path)
            store.upsert('A', '1', 'old', [1, 0])
            store.upsert('A', '1', 'new', [0, 1])
            store.upsert('B', '2', 'private', [1, 1])
            store.close()
            store = Store(path)
            self.assertEqual(len(store.rows('A')), 1)
            self.assertEqual(store.rows('A')[0][1], 'new')
            self.assertNotIn('private', str(store.rows('A')))
            store.delete('A', '1')
            self.assertEqual(store.rows('A'), [])
            self.assertEqual(len(store.rows('B')), 1)
            store.close()

if __name__ == '__main__':
    unittest.main()

Для інтеграції додайте тест межі компонента: замість мокання всього pipeline підмініть лише зовнішню залежність. В API відображайте очікувані помилки на стабільний статус і коротке повідомлення; внутрішній traceback залишається у захищеній діагностиці без секретів.

Самостійна лабораторна

Індексуйте 5 документів із двох уявних команд. У кожного є source, document_id, tenant і version. Оновіть один документ так, щоб кількість chunks змінилася, видаліть інший і перезапустіть процес. Доведіть, що старі записи не повертаються і чужа команда не знаходиться навіть за точним запитом. Для Chroma порівняйте approximate search з exact baseline на 20 питаннях і запишіть persistence path. Артефакти: lifecycle script, схема metadata, звіт із IDs до й після операцій.

Порядок самостійної роботи

  • До реалізації: запишіть гіпотезу, вхідні дані та критерій успіху.
  • Перший прохід: запустіть baseline й збережіть результати без прикрашання.
  • Другий прохід: змініть один фактор і повторіть перевірку на тих самих даних.
  • Завершення: підготуйте артефакти, поясніть невдачі та додайте regression tests.

Не копіюйте приклад без змін як завершену лабораторну. Використайте власні дані та принаймні один крайній випадок, якого немає у прикладі. Якщо зовнішня залежність недоступна, завершіть незалежні кроки й позначте конкретну інтеграційну перевірку unrun. Це чесніше, ніж підмінити її тривіальним успіхом.

Evaluation та самоперевірка

Автоматичні перевірки

  • Upsert одного ID не збільшує кількість записів.
  • Після відкриття БД заново дані доступні; delete прибирає результат.
  • Tenant A не отримує записи tenant B.

Ручна оцінка

  • Чи є політика видалення всіх chunks документа?
  • Чи manifest дозволяє перевірити сумісність моделі?
  • Чи approximate recall оцінено відносно exact search?
